# Onboarding (first-run setup): user scenarios and where each is tested

Index of what a person can do and see in the first-run setup of the phone app and which automated test protects it. Spec:
`docs/superpowers/specs/2026-10-09-onboarding-design.md`. Plan: `docs/superpowers/plans/2026-10-09-onboarding.md`. This is a coverage
catalogue, not a queue item. It continues `2026-10-09-app-shell-user-scenarios.md` (the shell around setup: navigation, themes, link dialog)
and `2026-10-08-builder-poc-user-scenarios.md`.

Actor: the owner, or a buyer: one person with a phone and, usually, a Wear OS 6 watch. There is no other role.

Test layers (all under `phone/` unless noted): **JVM** = `./gradlew :phone:testDebugUnitTest`, in `src/test/kotlin/com/seyedjafari/analogplus/phone/`;
**UI** = Compose tests on the phone emulator, `scripts/with_phone_emulator_lock.sh ./gradlew :phone:connectedDebugAndroidTest`
(`-Pandroid.testInstrumentationRunnerArguments.class=a.B,c.D` picks classes), in `src/androidTest/kotlin/com/seyedjafari/analogplus/phone/`;
**PY** = `python3 -m unittest tests.test_onboarding_lottie` (the animation files and their generator); **E2E** = `scripts/poc_e2e.sh` (two
emulators; it builds the face through the debug broadcast receiver and relays it by adb, so it never opens the phone UI: it is not affected by
the onboarding gate and passed unchanged). Test names below are `File.testName`; a file name alone means every test in it. `ui/` and
`ui/onboarding/` mean the sub-folder of the same tree.

How the UI tests drive the app: through `AppShell` with the real onboarding gate (`OnboardingHost`) inside `PinnedWindow` (a window of an exact
size in dp, whatever the emulator's size or orientation is) with the animation scale pinned (`LocalAnimationScale`), by pressing the same
buttons a person presses (`ShellFixture` in `OnboardingTestSupport.kt`); or through the real `MainActivity` over the app's real storage
(`RealStoreSnapshot` empties it and puts it back) where a scenario needs the system: a real Back key event, rotation, the app closed and
opened again, a VIEW intent. The one boundary that is replaced is the watch link: **the Wear Data Layer cannot be reached from an emulator**
(emulators cannot be paired without a Google sign-in), so the project's convention is a `FakeWatchTransport` (`ShellTestSupport.kt`) under the
**real** `TransportWatchStatusChecker`; tests that only need a given answer use `ControllableWatch` / `HangingWatch` (`WatchStatusChecker`
fakes) or the shell's `watchReady`. Nothing else is mocked: the controller, store, pages, animations and dialogs are the real ones.

## Not covered, and why

- **The real Wear Data Layer on a real paired phone and watch** (node and capability lookups, the "found" answer from a watch that really advertises the app,
  Wearable-app pairing followed by the automatic re-check on resume). The emulators cannot be paired (no Google sign-in in an automated run), and the owner's
  phone and watch were not available in this run. The logic runs on `FakeWatchTransport` under the real `TransportWatchStatusChecker` (rows 18 to 25) and the
  rows' words come from the same mapping as the Send screen. This is the first real exercise of that path: the manual checklist is group 0 in `docs/poc/README.md`
  and is still open.
- **A real process kill.** A test cannot kill its own process. Process death is a closed activity and a new activity, view model, controller and store over the same
  disk (33), plus new store and controller in the shell tests; the controller's in-memory parts (the tip, how the run started) are therefore lost exactly as
  they would be, and that is asserted (12, 40). What a real kill could add (the system restoring saved instance state of a half-composed page) is emulated
  with `StateRestorationTester` (34).
- **A real TalkBack run.** Semantics are asserted (headings, pane titles, live regions, names, sizes: rows 48 to 50), not the spoken output or focus order.
- **The system's own animator setting for the page slide** is covered (52, the test sets the real global setting and puts it back); a user toggling it while setup is on show is
  covered by the shell's `AnimationScaleLiveTest`, not repeated here.
- **Google's QR scanner** is not reachable during setup (the Library is behind the gate); a design from a scan arrives as the pending design of row 42.
- **The accounts page itself** (sign in with Google, the recovery passphrase) does not exist yet; only the slot and the stand-in page are tested (31, 32).
  The accounts plan owns its tests.
- **Localisation beyond resources** (spec out of scope): English wording only, compared with the logic's words.
- **Visual quality of the animations** (taste, motion) is judged by eye from the retaken pictures (47); tests guard structure, palette roles, last frames and caps.
- **Play Store link advice** for a missing watch app (arrives with the store listing; today the advice is generic and tested as such).
